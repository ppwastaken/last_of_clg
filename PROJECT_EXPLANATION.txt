PROJECT EXPLANATION - IaC Copilot
=================================

1. Project overview
-------------------

This project is called IaC Copilot.

IaC means Infrastructure as Code. It is the practice of writing infrastructure
configuration as files instead of manually creating resources from a dashboard.

Examples of infrastructure:
- Kubernetes Services, Deployments, StatefulSets, and PersistentVolumeClaims
- Redis, databases, and application workloads
- Cloud resources such as networks, instances, buckets, and managed services

This project lets a user describe infrastructure in normal English. The system
uses an LLM, such as Groq or Ollama, to generate Kubernetes YAML or Terraform
HCL. The generated configuration is validated, stored, reviewed by a human, and
only applied after approval.

Main idea:

    English prompt -> LLM generates IaC -> validate -> human review -> approve -> apply


2. Why this project is useful
-----------------------------

Writing Kubernetes YAML or Terraform manually can be difficult because:
- the syntax is strict
- indentation and nesting matter in YAML
- Kubernetes resources need matching selectors and labels
- Terraform must be valid HCL
- infrastructure changes can be risky

LLMs can help generate the first version of the config, but AI output should not
be trusted blindly. This project adds validation and a human approval workflow
so the generated infrastructure is reviewed before it is applied.


3. What the project does
------------------------

The project provides a complete workflow:

1. User enters a natural-language infrastructure request.
2. User chooses Kubernetes or Terraform output.
3. Backend sends the prompt to Groq or Ollama.
4. LLM returns generated IaC.
5. Backend validates the output.
6. If validation fails, backend sends the error back to the LLM and asks it to repair the config.
7. If validation passes, the request is saved as pending.
8. Human reviewer can inspect the generated config.
9. Reviewer can edit it with another prompt, approve it, reject it, or apply it after approval.
10. The system stores audit details such as attempts, validation output, status, and apply output.

--------------------

Backend:
- Python

Frontend:

Database:

Configuration:
- .env file


5. Main files and folders
-------------------------

backend/api.py
    FastAPI application. Defines endpoints for generate, list, edit, approve,
    reject, and apply.

backend/llm.py
    Handles communication with Groq or Ollama. It builds prompts for initial
    generation and prompt-based editing.

backend/service.py
    Contains the main business workflow. It calls the LLM, validates generated
    config, retries repair attempts, saves database records, and updates request
    statuses.

backend/validators.py
    Validates generated IaC. Terraform is validated with Terraform commands.
    Kubernetes is validated with offline YAML checks by default.

backend/apply.py
    Applies approved IaC. Kubernetes uses kubectl apply. Terraform uses
    terraform apply.

backend/models.py
    Defines database tables for requests and generation attempts.

backend/schemas.py
    Defines request and response models used by the API.

frontend/streamlit_app.py
    Streamlit user interface. It allows users to generate, review, edit,
    approve, reject, and apply infrastructure requests.

docker-compose.yml
    Starts the PostgreSQL database container.

.env
    Stores local configuration such as database URL, LLM provider, Groq API key,
    Ollama model, validation settings, and Kubernetes namespace.


6. User workflow
----------------

Step 1: Start PostgreSQL.

    docker compose up -d postgres

Step 2: Start the FastAPI backend.

    source .venv/bin/activate
    uvicorn backend.api:app --reload

Step 3: Start the Streamlit frontend.

    source .venv/bin/activate
    streamlit run frontend/streamlit_app.py

Step 4: Open the app in the browser.

    http://localhost:8501

Step 5: Enter a prompt.

Example:

    deploy a Redis cluster with 3 replicas and a persistent volume

Step 6: Choose output type.

Options:
- kubernetes
- terraform

Step 7: The app generates and validates IaC.

Step 8: If valid, the request appears in the approval queue as pending.

Step 9: Reviewer can approve, reject, edit, or apply after approval.


7. Edit with prompt feature
---------------------------

The reviewer can edit generated IaC using another natural-language prompt.

Example edit prompt:

    increase Redis storage to 5Gi and add CPU limit of 1 core

The backend sends the existing config and the edit instruction to the LLM. The
LLM returns a revised config. The backend validates the revised config again.

If the edited config passes validation, the request becomes pending again and
can be approved.

Applied requests are locked from editing. For already-applied infrastructure,
the user should create a new request or generate an update separately.


8. Validation
-------------

Validation means checking the generated IaC before it can be approved.

For Kubernetes, the default setting is:

    KUBECTL_DRY_RUN=client

This means the project performs offline YAML checks without needing a live
cluster during validation.

Kubernetes validation checks things like:
- YAML is parseable
- every resource has apiVersion
- every resource has kind
- every resource has metadata.name
- Service has selector and ports
- Deployment/StatefulSet selectors match pod template labels
- pod containers are placed under spec.template.spec.containers
- Redis StatefulSet includes important fields such as:
  - headless Service with clusterIP: None
  - Redis cluster mode enabled
  - volumeClaimTemplates
  - resource requests and limits
  - livenessProbe
  - readinessProbe

For Terraform, validation runs:

    terraform init -backend=false -input=false
    terraform validate -no-color


9. Repair loop
--------------

LLMs can make mistakes. If validation fails, the backend sends the validation
error back to the LLM and asks it to fix the config.

The number of attempts is controlled by:

    MAX_REPAIR_ATTEMPTS=3

Example:

The LLM may generate a Kubernetes Service without ports:

    kind: Service
    spec:
      clusterIP: None
      selector:
        app: redis

The validator rejects it because a Service needs spec.ports.

The backend sends this error back to the LLM:

    Service spec.ports must be a non-empty list

The LLM then tries again with a corrected Service that includes port 6379.


10. Approval and apply
----------------------

The project separates generation from apply.

Generating IaC only creates code and saves it in the database. It does not
create real infrastructure.

Applying IaC runs a real command:

For Kubernetes:

    kubectl apply -n default -f manifest.yaml

For Terraform:

    terraform apply -auto-approve -no-color

This is why approval is required before apply.

Status flow:

    pending -> approved -> applied

If apply fails:

    approved -> apply_failed


11. Kubernetes on the laptop
----------------------------

When Docker Desktop Kubernetes is enabled, Kubernetes runs locally on the
laptop. In that case:

- Streamlit runs on the laptop
- FastAPI runs on the laptop
- PostgreSQL runs in a Docker container
- Kubernetes runs through Docker Desktop
- Redis or other applied Kubernetes workloads run as pods inside the local Kubernetes cluster

The app uses the current kubectl context.

Check the current Kubernetes context:

    kubectl config current-context

For Docker Desktop, it is usually:

    docker-desktop

Check resources:

    kubectl get pods
    kubectl get svc
    kubectl get statefulset
    kubectl get pvc


12. Request statuses
--------------------

validation_failed
    The generated or edited config failed validation after all attempts.

pending
    The config passed validation and is waiting for review.

approved
    The reviewer approved the config.

rejected
    The reviewer rejected the config.

applied
    The approved config was applied successfully.

apply_failed
    The apply command ran but failed.


13. Database and audit history
------------------------------

The project stores important information in PostgreSQL:
- original prompt
- edit prompts
- generated config
- artifact type
- status
- validation output
- LLM model
- number of attempts
- reviewer note
- apply output
- generation/edit attempt history

This helps with auditing. A reviewer can understand what was requested, what the
AI generated, what validation found, and what happened during apply.


14. Important endpoints
-----------------------

POST /generate
    Generate and validate a new IaC request.

GET /requests
    List requests. Can be filtered by status.

GET /requests/{id}
    Get one request.

GET /requests/{id}/attempts
    View generation and edit attempts for one request.

POST /requests/{id}/edit
    Edit an existing request using a prompt and revalidate it.

POST /requests/{id}/approve
    Approve a pending request.

POST /requests/{id}/reject
    Reject a pending or validation-failed request.

POST /requests/{id}/apply
    Apply an approved request.


15. Demo explanation
--------------------

A simple way to explain the project:

    This is an AI-assisted Infrastructure as Code Copilot.
    A user describes infrastructure in plain English.
    The system uses Groq or Ollama to generate Kubernetes YAML or Terraform HCL.
    The generated config is validated automatically.
    If validation fails, the LLM gets the validation error and tries to repair it.
    If validation passes, the config goes to a human approval queue.
    The reviewer can edit it with another prompt, approve it, reject it, or apply it.
    The system stores the full history for audit and review.


16. Final conclusion
--------------------

IaC Copilot is not only a code generator. It is a safer workflow for AI-assisted
DevOps:

    generate -> validate -> repair -> review -> edit -> approve -> apply

The project shows how LLMs can help with infrastructure work while still keeping
validation, human control, and audit history in the process.
